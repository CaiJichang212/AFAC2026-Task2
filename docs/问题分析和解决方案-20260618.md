## 4. 源码根因分析

### 4.1 API 客户端把 HTML 错误页当成合法 Markdown

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py` 第 89-118 行。
- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py` 第 120-148 行。

关键逻辑：

1. `_post_chunk()` 只按 HTTP 状态码判断 4xx/5xx，状态码正常就进入 `_extract_markdown()`。
2. `_extract_markdown()` 如果发现响应不是 JSON，会直接执行 `_strip_markdown_fence(text)` 并返回原文本。
3. 因此 HTTP 200 的 HTML 网关页面会被视为成功结果。
4. `parse_chunk()` 第 69-73 行拿到这个 HTML 后立即 `_write_cache()` 并记录 `status=ok`。

这导致三层污染：

- `api_raw/{stem}/{chunk_id}.md` 缓存了错误页。
- `normalized/{stem}/{chunk_id}.md` 继续保存错误页。
- `merged/{stem}.md` 和 `submission_A_10.csv` 最终包含错误页。

### 4.2 缓存缺少内容有效性校验

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py` 第 169-201 行。

当前 cache meta 只记录：

- `chunk_id`
- `image_sha1`
- `api_url`

缺少：

- HTTP 状态码。
- Content-Type。
- 响应体类型。
- 是否通过 Markdown 合法性校验。
- 解析器版本或校验规则版本。
- 运行配置 hash。

所以一旦 HTML 错误页被写入缓存，后续 `--resume` 或普通重跑会继续复用错误结果。

### 4.3 合并级 resume 会掩盖旧错误

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py` 第 63-74 行。
- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py` 第 161-167 行。

`--resume` 默认开启，只要 `merged/{stem}.md` 存在，流程会直接返回旧合并结果，不再读取切块、不再调用 API、不再重新 normalize/dedup/table repair。

同时，这个分支调用 QC 时传入：

```python
chunk_count=0
failed_chunks=0
```

因此缓存命中的文件在 QC 中会显示 API 失败率为 0，丢失真实处理上下文。当前多个 QC 文件中 `chunk_count=0` 就是这个行为的结果。

### 4.4 质量门禁没有阻断提交

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py` 第 56-61 行。
- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py` 第 93-100 行。
- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/quality_gate.py` 第 73-113 行。

`QualityGate.check_file()` 返回 `QualityReport`，但 `_process_image()` 忽略返回值。`Pipeline.run()` 也没有汇总所有文件的 QC 结果，最后直接调用 `SubmissionWriter().write(...)`。

`SubmissionWriter` 只验证 CSV 结构：

- 列名。
- 行数。
- 文件名集合。
- 文件名重复。

它不检查每个文件的 QC 是否通过，所以 `high_duplication`、`html_broken`、`too_short` 等风险不会阻断输出 CSV。

### 4.5 `RetryPlanner` 已实现但没有接入主流程

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/retry_planner.py`

代码搜索结果显示 `RetryPlanner` 只在测试中被引用，主流程没有调用。配置文件中虽然有：

但实际运行不会因为 `empty_output`、`too_short`、`html_broken`、`api_failure_ratio_high` 或 `high_duplication` 自动重跑。

### 4.6 配置声明了并发，但实际 API 请求是串行的

问题位置：

- `/Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py` 第 102-130 行。

1. 100 张图三小时复现目标很难达成。

当前 3 个文件被拦住是因为 HTML 错误页重复行很多，触发了 `high_duplication`，不是因为系统识别出了“服务器繁忙”页面。`1c3ec...` 就因为重复率没超过阈值而漏检。

## 5. 解决方案

### 5.1 P0：先阻断 HTML 错误页进入缓存和提交

修改 `FinixApiClient`，在写缓存前做响应有效性校验。

建议规则：

1. 在 `_post_chunk()` 中读取 `response.headers.get("content-type")`，记录到日志。
2. `_extract_markdown()` 返回前增加 `validate_markdown_response(text)`。
3. 以下情况一律视为可重试 API 错误，不得写入 `.md` cache：
   - 文本以 `<!DOCTYPE html` 或 `<html` 开头。
   - 包含 `<head>`、`<body>` 且不是单纯文档表格片段。
   - 包含 `服务器繁忙`、`顾客太多`、`J_retry_link`、`showTextWait`、`支付宝版权所有`。
   - 包含明显网关等待页资源，如 `alipayobjects.com`、`wait-*.css`。
4. 允许保留 FinixDoc-VL 输出的 `<table>...</table>`，不要把所有 HTML 标签都误判为错误。

同时补充单测：

- HTTP 200 + JSON result Markdown：通过并写 cache。
- HTTP 200 + Markdown fence：通过并写 cache。
- HTTP 200 + `<!DOCTYPE html><title>服务器繁忙</title>`：抛出 `FinixApiError`，不写 cache。
- HTTP 200 + 含 `<table>` 的合法 Markdown：通过。

### 5.2 P0：清理已污染缓存和合并结果

在修复 API 校验后，需要清理当前输出目录中的污染产物，否则 `--resume` 会继续复用旧结果。

建议先定位：

```bash
rg -l "J_retry_link|showTextWait|服务器繁忙|<!DOCTYPE html>" \
  /Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/outputs/run_A_10/api_raw \
  /Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/outputs/run_A_10/normalized \
  /Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/outputs/run_A_10/merged
```

然后对受影响文件使用独立 `work_dir` 重新跑，或在确认只删除运行产物的前提下删除这些 stem 下的：

- `api_raw/{stem}`
- `normalized/{stem}`
- `merged/{stem}.md`
- `qc/{stem}.json`

不要修改 `data/` 原始输入。

### 5.3 P0：让质量门禁真正阻断提交

调整 `Pipeline.run()`：

1. `_process_image()` 返回 markdown 和 `QualityReport`。
2. `Pipeline.run()` 汇总所有文件的 QC。
3. 只要存在 `not report.passed`，默认不生成正式 submission，或者生成 `submission.draft.csv` 并以非 0 状态退出。
4. 最终 `submission.csv` 必须满足：
   - CSV 结构校验通过。
   - 每个文件 QC 通过。
   - 全局无异常 HTML 标记。

建议新增全局报告：

```text
{work_dir}/qc/summary.json
```

字段包含：

- `passed`
- `failed_files`
- `risk_counts`
- `csv_report`
- `api_call_counts`

### 5.4 P0：接入失败重跑机制

把 `RetryPlanner` 接入 `Pipeline._process_image()`：

1. 首次处理后执行 `QualityGate.check_file()`。
2. 如果失败，根据 `RetryPlanner.plan()` 决定是否重跑。
3. 对 `service_busy_html`、`api_failure_ratio_high`：
   - 降低并发。
   - 增加指数退避和 jitter。
   - 对失败 chunk 强制 `force_api=True`。
4. 对 `too_short`：
   - 增大 overlap。
   - 或降低 window height 后重切。
5. 对 `high_duplication`：
   - 先检查是否含 HTML 错误页；如含 HTML，必须重跑污染 chunk。
   - 若无 HTML，再进入接缝去重策略调参。

重跑次数使用 `quality.max_reruns_per_file` 控制，超过次数仍失败则阻断提交。

### 5.5 P1：重做缓存有效性和 resume 语义

建议将缓存分为三层，并分别设置 meta：

1. `api_raw`：只保存通过响应合法性校验的 API Markdown；失败响应另存到 `api_error/{stem}/{chunk_id}.txt`，避免污染 raw cache。
2. `normalized`：meta 记录 normalizer 版本和输入 raw sha1。
3. `merged`：meta 记录 manifest sha1、raw cache sha1 列表、merge 配置 hash、table repair 版本。

`_read_merged()` 不能只看文件存在，应校验 meta 是否匹配当前：

- 原图 hash。
- chunk manifest。
- merge 配置。
- normalizer/table repair 版本。
- API URL。

否则修改配置后会继续复用旧合并结果。

### 5.6 P1：实现真实且可控的 API 并发

当前串行请求太慢，但盲目提高并发可能加剧“服务器繁忙”。建议实现自适应并发：

1. 使用 `ThreadPoolExecutor` 或 `asyncio` 并发处理 chunk。
2. 加 per-user semaphore，确保单个 `userId` 不超过 `per_user_concurrency`。
3. 遇到 `service_busy_html`、429、5xx、timeout 时：
   - 全局并发临时降级。
   - 对该 userId 做短时间冷却。
   - 使用指数退避加随机 jitter。
4. 日志记录每个请求的调度信息，便于判断并发是否触发网关限流。

在没有完成自适应前，建议保守使用 `concurrency=1 or 2`，优先保证结果有效性。

### 5.7 P1：修正 `--limit` 的抽样语义

为了让 smoke test 同时覆盖长条和表格，建议新增参数：

- `--limit_per_dir N`：每个输入目录取前 N 张。
- 或 `--sample_each_input N`：每个输入目录取 N 张。

现有 `--limit` 可以保留为全局限制，但文档和脚本中应明确它是合并后的全局截断。

`test.sh` 的部分数据测试建议改为每类各取 5 张，避免只验证长条链路。

### 5.8 P1：增强 QC 检查

新增质量风险：

- `service_busy_html`
- `full_html_page`
- `gateway_error_page`
- `raw_cache_invalid`
- `merged_from_stale_cache`

QC 检查建议：

1. 在 merged 文本中扫描 `<!DOCTYPE html>`、`<html>`、`<head>`、`<body>`、`J_retry_link`、`服务器繁忙`。
2. 对 raw cache 执行同样扫描，发现即判失败。
3. 对 `high_duplication` 输出 top duplicate lines，便于判断是接缝重复还是错误页重复。
4. 将 `chunk_count=0` 的 resume QC 标记为 `from_merged_cache=true`，不要让它伪装成完整处理。

### 5.9 P2：完善日志可观测性

建议每次运行生成 `run_id`，并在 `run.jsonl` 中追加：

- `run_start`
- `config_snapshot`
- `image_start`
- `chunk_created`
- `api_call`
- `api_error`
- `cache_hit`
- `file_qc`
- `file_rerun`
- `submission_written`
- `run_end`

`api_call` 至少增加：

- `run_id`
- `http_status`
- `content_type`
- `response_sha1`
- `response_chars`
- `error_type`
- `error_summary`
- `from_cache`
- `attempt`

这样后续无需打开 raw 文件即可定位“ok 是否真的有效”。

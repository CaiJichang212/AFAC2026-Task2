# 图片切分优化方案

## 1. 背景与目标

当前项目已经具备基础切分能力：

- `long_strip` 使用固定高度纵向滑窗。
- `table_page` 和 `normal_page` 使用均匀网格切分。
- `LayoutSentry` 已能产出内容边界、水平/垂直空白带、表格线密度等轻量版面提示。

但从 `docs/赛题数据统计分析.md` 和 `docs/FinixDoc-VL的图片尺寸说明.md` 对照看，当前切分策略仍偏 MVP：参数语义不清、没有充分利用 FinixDoc-VL 的可接受尺寸范围，也没有把 API 调用次数、超时风险、表格切线质量统一优化。

本方案目标：

1. 在不超过 FinixDoc-VL 单次输入硬上限的前提下，合理增大切片，降低 API 调用次数。
2. 对 long/table/normal 三类图片采用不同像素预算和切线策略。
3. 利用 `LayoutSentry` 的空白带、内容边界和线密度，减少切块截断、重复和表格结构破坏。
4. 保持切分结果可追溯、可缓存、可复现，不引入任何额外大模型或外部 API。

## 2. 约束与数据依据

### 2.1 FinixDoc-VL 尺寸约束

根据 `docs/FinixDoc-VL的图片尺寸说明.md`：

| 参数 | 值 | 方案含义 |
| --- | --- | --- |
| `min_pixels` | 4096 | 极小切片需放大或合并，避免不可识别。 |
| `max_pixels` | 16,777,216 | 单次上传硬上限，任何切片不得超过。 |
| 推荐工作点 | 1M-4M | 高稳定性保守区间，不是硬上限。 |
| 接近 16M | 延迟显著增加 | 只用于少量整页参考或兜底，不作为默认。 |

API 文档还提示：图片或切片过大时可能处理时间过长甚至请求超时；统一 apiKey 会带来额外安全校验耗时。因此，策略应在“减少请求数”和“避免超时”之间取平衡。

### 2.2 数据集压力

当前 300 张训练+A榜图片理论切片数随目标像素变化如下：

| 目标像素 | 理论切片数 |
| ---: | ---: |
| 4M | 5,970 |
| 5M | 4,893 |
| 6M | 4,044 |
| 8M | 3,032 |
| 10M | 2,501 |
| 12M | 2,096 |
| 16M | 1,559 |
| 16.78M | 1,488 |

结论：全局固定 4M 太保守，会显著增加 API 请求数；但全局逼近 16M 又会增加超时和结构粗糙风险。更合理的做法是按文档类型动态使用 `target_pixels`、`safe_max_pixels` 和 `hard_max_pixels`。

## 3. 当前主要问题

### 3.1 配置语义与实际行为不一致

`configs/default.yaml` 中 `chunk.max_chunk_pixels=4,000,000`，但当前实现：

- long 默认 `1500 x 4000 ≈ 6M`。
- table 网格切分后再加 overlap，实际切片通常超过 4M。

这不一定是坏事，因为 4M 不是硬上限；真正的问题是配置名称叫 `max_chunk_pixels`，但实际并不表示“最大值”。这会误导调参和测试。

### 3.2 long 切片没有像素上限保护

`LongStripChunker` 只按固定 `long_window_height` 切分，没有根据图片宽度动态调整窗口高度。当前 long 宽度多为 1500px，4000px 高约 6M，尚可接受；但如果 B榜出现更宽长图，单片像素会线性增大，可能逼近甚至超过安全上限。

### 3.3 table 切线质量不足

`TableGridChunker` 目前按几何均分行列切块，没有利用：

- `LayoutHints.crop_box`
- `horizontal_blank_bands`
- `vertical_blank_bands`
- `table_line_density`
- `column_count`

这会导致切线穿过表头、单元格、横线或竖线，损害表格 TEDS 和后续 HTML 合并。

### 3.4 白边没有进入切分流程

`LayoutSentry` 已计算内容边界 `crop_box`，但切分仍从整图 `(0, 0, width, height)` 开始。大图白边会浪费像素预算，降低有效文本比例，增加 API 耗时。

### 3.5 manifest 信息不足

当前 manifest 只记录 bbox、row、col、overlap 等基础信息。缺少：

- 实际切片像素数。
- 是否最后一行/最后一列。
- 原图内容裁剪边界。
- 切线来源：固定窗口、空白带、网格、表格线。
- 风险标签：超过 safe max、切在非空白区域、窄小残片等。

这些信息缺失会影响缓存追溯、阅读顺序恢复、表格合并和质量门禁。

## 4. 优化原则

1. **4M 是保守推荐，不是硬上限。** 不应为了卡 4M 牺牲调用次数。
2. **16.78M 是硬上限，不是常规目标。** 常规策略应留出安全余量。
3. **long 与 table 分开调参。** long 阅读流单向，可适当增大切片；table 结构密集，应更保守并优先保证切线质量。
4. **overlap 后也要校验像素。** 目标像素应按最终 bbox 计算，而不是只按基础网格计算。
5. **先裁有效区域，再切分。** 使用 `crop_box + margin` 提升有效像素占比。
6. **切分结果必须可追溯。** 所有切片应能映射回原图坐标和切线决策来源。

## 5. 推荐配置模型

建议把当前单一 `max_chunk_pixels` 改为分层配置：

```yaml
chunk:
  hard_max_pixels: 16777216
  safe_max_pixels: 12000000
  min_pixels: 4096

  crop_margin_px: 24

  long:
    target_pixels: 6000000
    safe_max_pixels: 8000000
    max_window_height: 4000
    min_window_height: 1800
    vertical_overlap: 320
    blank_band_search_px: 360

  table:
    target_pixels: 6000000
    safe_max_pixels: 8000000
    full_page_max_pixels: 8000000
    horizontal_overlap: 160
    vertical_overlap: 220
    cut_search_px: 260

  normal:
    full_page_max_pixels: 12000000
    target_pixels: 8000000
```

说明：

- `hard_max_pixels` 对齐 FinixDoc-VL 单次输入上限。
- `safe_max_pixels=12M` 是全局安全保护，避免常规切片逼近硬上限。
- long 默认 `target_pixels=6M`，可显著减少调用次数，且当前 1500px 宽长条图约等于 4000px 高窗口。
- table 默认 `target_pixels=6M`、`safe_max_pixels=8M`，比 long 更保守，避免表格结构过密导致超时或结构粗糙。
- normal 页低于 12M 可整页尝试，减少不必要切块。

## 6. 分类型切分策略

### 6.1 LongStripChunker

目标：减少请求数，同时避免超宽长图导致单片失控。

推荐算法：

1. 计算内容区域：`content_box = expand(hints.crop_box, margin)`。
2. 使用内容宽度计算自适应窗口高度：

   ```text
   target_height = floor(long.target_pixels / content_width)
   safe_height = floor(long.safe_max_pixels / content_width)
   window_height = min(long.max_window_height, safe_height)
   window_height = max(window_height, long.min_window_height)
   ```

3. 生成基础纵向窗口。
4. 在 `y1 ± blank_band_search_px` 范围内寻找最近水平空白带。
5. 若找到空白带，切线落在空白带中心；若找不到，使用固定切线并记录风险。
6. overlap 后重新计算最终 bbox 像素，若超过 `safe_max_pixels`，缩短窗口或降低 overlap。
7. 对最后一个残片：
   - 若残片像素过小，合并到上一片。
   - 若合并后超过 safe max，则保留残片并记录 `small_tail` 风险。

预期效果：

- 当前 long 数据维持约 6M 单片，调用次数比 4M 明显更低。
- 对更宽 B榜长图有安全上限保护。
- 空白带切线减少文字截断和接缝重复。

### 6.2 TableGridChunker

目标：降低表格结构破坏，控制 overlap 后像素不超过 safe max。

推荐算法：

1. 先应用 `content_box = expand(hints.crop_box, margin)`，减少白边。
2. 若 `content_pixels <= table.full_page_max_pixels`：
   - 整页上传，作为全局参考。
3. 若 `content_pixels <= hard_max_pixels` 且 `table_line_density` 较低：
   - 可整页上传或少量切分，降低拼接复杂度。
4. 对高像素/高线密度表格：
   - 先按 `target_pixels` 估算基础 `rows x cols`。
   - 把 overlap 纳入估算，确保最终 bbox 不超过 `table.safe_max_pixels`。
   - 对每条候选横切线，在 `±cut_search_px` 内搜索水平空白带或低墨迹密度区域。
   - 对每条候选竖切线，在 `±cut_search_px` 内搜索垂直空白带或低墨迹密度区域。
   - 避免切线落在高密度横线/竖线或表头密集区域。
5. 对跨列/跨行风险高的表格，保留较小 overlap，并依赖后处理做重复表头合并。

预期效果：

- table 请求数控制在 6M-8M 工作区间。
- 切线更可能落在行间/列间，减少单元格截断。
- manifest 中 row/col/bbox 更适合后续表格合并。

### 6.3 PageChunker / normal_page

目标：避免普通页被不必要切碎。

推荐策略：

1. 若 `content_pixels <= normal.full_page_max_pixels`，直接整页上传。
2. 若超过阈值但线密度低，按纵向或轻量网格切分。
3. 若检测到多栏：
   - 先按栏切分或记录 `column_count`，供阅读顺序恢复使用。
4. normal 页不应直接完全复用 table 网格策略，否则会增加拼接和阅读顺序风险。

## 7. Manifest 与命名改造

建议 manifest 记录以下字段：

```json
{
  "file_name": "xxx.jpg",
  "width": 1500,
  "height": 80299,
  "doc_type": "long_strip",
  "content_box": [0, 12, 1500, 80270],
  "chunk_policy": "long_dynamic_v1",
  "chunks": [
    {
      "chunk_id": "...",
      "image_path": "...",
      "bbox": [0, 0, 1500, 4000],
      "row": 0,
      "col": 0,
      "chunk_pixels": 6000000,
      "overlap": {"top": 0, "bottom": 320, "left": 0, "right": 0},
      "is_last_row": false,
      "is_last_col": true,
      "cut_source": "blank_band",
      "risk_flags": []
    }
  ]
}
```

切片文件名建议使用可追溯格式：

```text
{原图stem}__r{row}_c{col}__x{x0}_y{y0}_w{w}_h{h}.jpg
```

这样能同时满足 API `fileName` 参数要求、缓存追踪和人工排错。

## 8. API 调用次数与运行时间控制

### 8.1 不再用 4M 作为全局上限

4M 适合作为“保守稳定参考”，但不是硬上限。若全局固定 4M，300 张图理论切片数约 5,970；若提升到 6M，理论切片数约 4,044；若提升到 8M，理论切片数约 3,032。考虑 API 安全校验耗时，减少请求数对总耗时很关键。

### 8.2 推荐默认组合

| 类型 | 目标像素 | 安全上限 | 策略 |
| --- | ---: | ---: | --- |
| long | 6M | 8M | 保持全宽纵向滑窗，动态高度，优先空白带切线。 |
| table | 6M | 8M | 内容区网格，切线贴近空白/低密度区域。 |
| normal | 整页优先 | 12M | 低于 12M 整页，高于阈值再切。 |
| 全局 | - | 16.78M | 任何切片不得超过硬上限。 |

### 8.3 失败重试策略

若某切片 API 超时或空输出：

1. 首次重试保持原切片，排除瞬时网络问题。
2. 第二次失败后，把该切片按短边或主阅读方向二分。
3. 对 table 切片，优先二分为更小网格，并增加 overlap。
4. 对 long 切片，降低目标像素到 4M，并保留原 bbox 关系。

## 9. 测试与验收标准

### 9.1 单元测试

新增或强化以下测试：

1. `test_long_dynamic_height_respects_safe_max_pixels`
   - 构造宽图，验证 long 窗口会随宽度降低高度。
2. `test_table_overlap_included_in_pixel_budget`
   - 构造大表格，验证加 overlap 后仍不超过 table safe max。
3. `test_crop_box_applied_with_margin`
   - 构造大白边图，验证 bbox 基于内容区扩展，不裁掉内容。
4. `test_last_row_col_overlap_metadata`
   - 验证最后一行/列的 `right/bottom` overlap 为 0。
5. `test_table_cut_adjusts_to_blank_band`
   - 构造表格空白间隔，验证切线优先移动到空白带。
6. `test_chunk_manifest_contains_policy_fields`
   - 验证 manifest 包含 `chunk_pixels`、`cut_source`、`risk_flags`。

### 9.2 数据级 dry-run 验收

对训练集和 A榜执行 dry-run，只生成 profile、manifest 和切片统计：

- 所有切片 `chunk_pixels <= hard_max_pixels`。
- 常规切片 `chunk_pixels <= safe_max_pixels`，超过需有 `risk_flags`。
- long 平均切片数不应显著高于当前 6M 策略。
- table 切片边界应尽量贴近空白带或低密度带。
- manifest 可完整覆盖原图内容区，无空洞。

### 9.3 API 小样本验收

每类抽取样本：

- long：短、中、极长各 2 张。
- table：低像素、中像素、极大表格各 2 张。
- normal：若存在，抽 2 张。

对比旧策略与新策略：

| 指标 | 期望 |
| --- | --- |
| API 请求数 | 新策略不高于旧策略，long 应明显下降或持平。 |
| 超时率 | 不高于旧策略。 |
| 空输出率 | 不高于旧策略。 |
| 接缝重复 | 不高于旧策略。 |
| 表格截断 | 新策略应减少。 |
| 人工阅读顺序 | 不低于旧策略。 |

## 10. 分阶段实施计划

### Phase 1：配置与像素预算闭环

- 增加分类型配置：`hard_max_pixels`、`safe_max_pixels`、`long.target_pixels`、`table.target_pixels` 等。
- 修改 long 窗口高度计算，按宽度动态控制像素。
- 修改 table 网格估算，把 overlap 纳入像素预算。
- 修正最后行/列 overlap 元数据。
- 增加像素预算相关单测。

### Phase 2：内容区裁剪与 manifest 增强

- 使用 `crop_box + margin` 生成内容区坐标。
- 所有切片 bbox 基于内容区生成，但仍记录原图坐标。
- manifest 增加 `content_box`、`chunk_pixels`、`cut_source`、`risk_flags`。
- 增加 dry-run 统计命令或报告输出。

### Phase 3：版面感知切线

- long：在目标切线附近搜索水平空白带。
- table：在网格候选线附近搜索水平/垂直空白带或低密度投影区。
- 对找不到安全切线的块记录风险，供质量门禁和人工抽查。

### Phase 4：失败切片自适应重切

- API 超时/空输出后，对失败切片自动二分。
- 失败重切仍复用原始 bbox 与 manifest 父子关系。
- 质量门禁中记录失败切片、重切次数和最终状态。

## 11. 推荐优先级

| 优先级 | 改进项 | 原因 |
| --- | --- | --- |
| P0 | 分类型像素预算与 hard/safe max | 先解决配置语义和 API 尺寸风险。 |
| P0 | long 动态高度 | 兼顾调用次数和 B榜泛化。 |
| P0 | table overlap 后像素校验 | 防止表格切片实际超过预期。 |
| P1 | crop_box 去白边 | 提高有效像素占比，减少无效输入。 |
| P1 | 表格空白带/低密度切线 | 直接提升表格结构完整性。 |
| P1 | manifest 增强 | 支撑后续去重、合并、审计。 |
| P2 | API 失败自适应重切 | 降低极端样本失败率。 |

## 12. 结论

当前策略不应简单改成“所有切片限制在 4M 以下”。4M 是稳定参考点，不是硬上限。更合理的优化方向是：

- long 使用约 6M 的较大切片，控制调用次数；
- table 使用 6M 左右、8M 安全上限的结构优先切片；
- normal 低于 12M 尽量整页；
- 所有类型都受 16.78M 硬上限保护；
- 使用内容区、空白带和低密度投影提升切线质量；
- 用 manifest 和测试把像素预算、切线来源和风险标记闭环。

该方案能更充分利用 FinixDoc-VL 的输入尺寸能力，同时避免把请求数推得过高，并为后续表格合并、接缝去重和质量门禁提供更可靠的输入。

## 二、真正的问题（按严重性排序）

### 1. 【严重】把限流 HTML 错误页当成 markdown 写入了最终结果

[`finix_api.py#L107-141`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L107-L141) 的 `_post_chunk` / `_extract_markdown` 只看 HTTP 状态码：
- 限流时支付宝返回的是 `200 OK + HTML "顾客太多"`；
- `json.loads` 失败 → 走 `_strip_markdown_fence(text)` 直接返回整页 HTML；
- 然后被当成"成功"`status=ok` 写入缓存与 `merged/*.md`，并最终塞进 CSV。

证据：[`merged/3ed0a71a-...md#L43-L80`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/outputs/run_A_10/merged/3ed0a71a-7641-4a48-8aab-9c618f1aa387.md#L43-L80) 整段 `<!DOCTYPE html>...顾客太多`；`grep -rl 顾客太多 outputs/run_A_10/api_raw` 命中 20 个 chunk；4 个 merged 文件被污染。这是评测分数被严重拉低的头号原因。

### 2. 【严重】`retryable_error` 占比 58 %，用户 ID 轮询并未真正起到分流作用

`run.jsonl` 显示常见错误形如：`elapsed_ms=2`、`elapsed_ms=5`，几乎瞬间失败 → 服务端速率限制/拒绝。当前逻辑：
- [`finix_api.py#L150-158`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L150-L158) `_next_user_id` 简单 round-robin，没有"出错冷却"。`_disabled_user_ids` 在调用栈中**从未被写入**，等于无效字段。
- [`finix_api.py#L83`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L83) 重试 backoff 仅 `2**retry_index`（1s/2s/4s），且各 chunk 之间又**完全串行**（[`pipeline.py#L115-129`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py#L115-L129) 用 for 循环逐个 `parse_chunk`），`concurrency` 配置实际从未生效。
- 文件 `2f76ff1e...`（最高图）单文件触发了 250 次调用、其中很多是同一 chunk 的多次重试，仍是大量 retryable_error。

### 3. 【严重】QC 漏检"伪成功" → 提交照常生成

[`quality_gate.py#L73-113`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/quality_gate.py#L73-L113) `check_file` 只检查 `chars / duplication_ratio / api_failure_ratio / html_broken(table/tr/td/th)` 等。HTML 错误页里：
- `<table>` 等都是闭合的 → 不触发 `html_broken`；
- chars 远超阈值 → 不触发 `too_short`；
- `failed_chunks=0`（API 返回的是 200，被当 ok）→ `api_failure_ratio_high` 不触发。

所以 QC 的 `passed=true / risks=[]` 文件里也有可能藏着 HTML 错误页（[`qc/0e28acf1-...json`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/outputs/run_A_10/qc/0e28acf1-b5e0-4925-808d-028affe0517a.json) 这种"通过"也无法证明 chunk 全部正确）。`chunk_count=0` 还说明 resume cache 命中后根本不知道历史 chunks 数（[`pipeline.py#L66-74`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py#L66-L74) 直接传 `chunk_count=0`），让 QC 进一步失真。

### 4. 【严重】污染会被 cache 永久固化

[`finix_api.py#L186-201`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L186-L201) `_write_cache` 写入 raw + meta；`_read_cache` 只校验 `chunk_id / image_sha1 / api_url`，不校验**内容质量**。一旦把 HTML 错误页写进 `api_raw/{stem}/{chunk_id}.md`，下一次 `--resume`（默认开启）会直接返回那段 HTML 当 `source=cache`，**不重新调 API**。同理 `_read_merged` 也无质检（[`pipeline.py#L161-167`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py#L161-L167)）。

### 5. 【中】RetryPlanner 是孤儿模块

[`retry_planner.py`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/retry_planner.py) 设计了"按风险点回退窗口、加重叠、降并发"的策略，但 `pipeline.run` 只跑一遍，没有任何处理 QC 结果的回路。即使 QC 标了 `high_duplication` 也不会重跑、不会调整切片参数。

### 6. 【中】Dedup 对 long_strip 实际不工作

[`dedup.py#L49-64`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/dedup.py#L49-L64) `_can_dedup` 要求 `_chunks_overlap`，里面同时校验 `x_overlap > 0` **和** `y_overlap > 0`。可是 long_strip 切片是垂直滑窗，bbox 的 x 区间相同但**没有"x 重叠 > 0"的判定** —— 看代码 `min(ax1,bx1) - max(ax0,bx0) = width - 0 = width > 0` ✓；但 `y_overlap` 取上 chunk 与下 chunk 的 y 区间，是 `min(ay1, by1) - max(ay0, by0)`。当滑窗设置 `y0 = max(y1 - overlap, y0+1)` 时，前一窗 (0..y1)、后一窗 (y1-overlap..y2) → y_overlap = `y1 - (y1-overlap) = overlap > 0` ✓。所以理论上能触发——**但**：`_find_prefix_suffix_overlap` 是字符级前后缀严格匹配，VLM 多次识别同一区域文字会有微小差异（错字、空白、标点），严格 `==` 几乎匹配不到，落到 `SequenceMatcher` 时步长 25 还要求 `ratio >= 0.88`，对长文档的相似度计算不稳定。这就是为什么 `2f76ff1e...` chars 9.4 万、duplication_ratio 0.63 的根因：**真重叠没去掉，merge 时把重叠区当成两份正文拼接**。

### 7. 【中】CSV 字段未做换行/转义保护

`SubmissionWriter` 用 pandas 默认参数写出（[`submission.py#L20-23`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/submission.py#L20-L23)），ground_truth 中含真实换行的字段必须用双引号闭合且双引号需转义。pandas `to_csv` 默认 `quoting=QUOTE_MINIMAL` + `quotechar='"'`、`doublequote=True` 是正确的，因此目前 9834 行可以被 pandas 重新读回 10 行；**但任何用 `wc -l`、Excel、或纯文本切分的下游工具都会出错**。建议显式锁死 `quoting=csv.QUOTE_ALL`，并在 `_validate` 中**用 pandas 重新读后比较 ground_truth 长度**，避免静默不一致。

### 8. 【小】并发配置失效、日志没记录"返回内容长度/HTML 标记"

- [`pipeline.py#L102-112`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/pipeline.py#L102-L112) 每次 `_parse_chunks` 都新建 `FinixApiClient`，所以 `_user_index` 每文件都从 0 起。
- `concurrency` 被 client 接受但全程串行执行，等同摆设。
- `run.jsonl` 没有记录响应字节数 / content-type / 是否 HTML，难以快速定位限流。

### 9. 【小】`profile.path` 是绝对路径写进 `profiles/*.json`，跨机/容器复现会失效，且 `.env` 路径泄露风险

仅是工程层面建议，可后置处理。

## 三、解决方案

按优先级与工作量给出**最小可行修复**与**结构性改造**两层。

### A. 最小修复（针对当前榜分流血点，必做）

1. **修 `finix_api._post_chunk`：识别 HTML/限流为 retryable**  
   在 [`finix_api.py#L107-118`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L107-L118) 的 `_post_chunk` 里增加：
   - 读 `Content-Type`，若包含 `text/html`，无论 200 都抛 `FinixApiError("retryable: html response")`；
   - 再做正文兜底：`text` 命中 `<!DOCTYPE html>` / `顾客太多` / `服务器繁忙` / `<title>.*</title>` → retryable；
   - 把"`success=false`/限流码 (如 429、`code` 含 'rate'/'busy')"也归到 retryable 而非永久 fail。
   这是修复 #1、#2、#4 的核心。

2. **缓存写入前做"内容质检"**  
   `_write_cache` 调用前判断：内容若以 `<!DOCTYPE`、`<html`、或长度异常小（如 `<10`）则**不写缓存且 raise retryable**。[`finix_api.py#L186-201`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/finix_api.py#L186-L201)

3. **清理已有"中毒"缓存**  
   一次性脚本：`grep -rl '<!DOCTYPE\|顾客太多\|服务器繁忙' outputs/run_A_10/api_raw outputs/run_A_10/merged` 找到的 .md 与对应 .json 全部删除，再用 `--resume` 重跑。

4. **限流退避升级 + 用户 ID 冷却**  
   - 检测到 `retryable: html / 429 / 5xx` 时，把 `user_id` 加入 `_disabled_user_ids`，并 sleep 一个递增 + 抖动的时间（如 `min(60, 5 * 2**retry_index) + random.uniform(0,2)`）；
   - `_next_user_id` 在 `_disabled_user_ids` 不全满时跳过被禁；全满时全局 sleep 30s 再清空。
   - `max_retries` 从 3 升到 6（大图很容易碰到限流）。

5. **QC 增加"HTML 残留"检测，并阻断提交**  
   [`quality_gate.py`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/quality_gate.py) 增加：
   ```python
   if "<!doctype html>" in markdown.lower() or "顾客太多" in markdown or "服务器繁忙" in markdown:
       risks.append("html_error_leak")
   ```
   并在 `Pipeline.run` 末尾，遇到任何 `html_error_leak` 直接 raise，**绝不让此类提交成型**。

6. **CSV 写入显式 `quoting=csv.QUOTE_ALL`**  
   [`submission.py`](file:///Users/lzc/TNTprojectZ/AprojectZ/AFAC2026-Task2/finix_restore/submission.py) 中：
   ```python
   df.to_csv(output_csv, index=False, encoding="utf-8", lineterminator="\n", quoting=csv.QUOTE_ALL)
   ```
   并在 `_validate` 中校验 `df["ground_truth"].str.len()` 与原 rows 一致，避免编码、转义错位。

### B. 结构性改造（建议下一阶段做）

7. **接入 `RetryPlanner`**：在 `_process_image` 拿到 QC 后，若 `passed=false` 且未达 `max_reruns_per_file`，按 plan 缩 `long_window_height`、调 `overlap`，删掉对应缓存后重切重跑。这能直接把 #5、#6 的副作用收敛。

8. **真正的并发**：按 `user_ids` 数把 chunk 分发到 `ThreadPoolExecutor`，每个 worker 绑定一个 user_id，互相独立做退避。当前 5 个 user_id × 串行，正好放大了排队延迟（最长一次 ok 调用 183 秒）。

9. **强化 dedup**：long_strip 用"行级"指纹去重 + 重叠区只保留一份。具体做法是按行 hash 寻找 LCS（或滚动哈希），不再依赖 SequenceMatcher 字符级近似。

10. **缓存 + chunk_count 透传**：`_read_merged` 命中时也读取 `manifest.json` 的 chunk 数，传给 `quality_gate.check_file`，让 metrics 可信。

11. **日志增强**：`run.jsonl` 增加 `response_bytes`、`content_type`、`is_html`、`http_status` 字段，方便事后定位限流。
